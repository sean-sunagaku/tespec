# ASCII Wireframe — 画面設計 & ワイヤーフレーム生成

機能要件から画面構成を対話で洗い出し、ASCII アートで各画面をワイヤーフレーム化するスキル。

## ワークフロー

```
Phase 1: 機能要件の洗い出し
  ↓ 対話で画面・操作・遷移を固める
Phase 2: ASCII ワイヤーフレーム生成
  ↓ 各画面のレイアウトを ASCII ボックスで描画
Output: 画面遷移図 + 各画面ワイヤーフレーム + 操作一覧
```

---

## Phase 1: 機能要件の洗い出し

### 目的
「何の画面が必要で、各画面で何ができるか」を対話で明確にする。

### 進め方

**Step 1: 全体像の把握**

ユーザーに以下を確認する（AskUserQuestion で構造化して聞く）:

- この機能の目的は何か（1文で）
- 主要なユーザーアクションは何か
- 入力と出力は何か

**Step 2: 画面の列挙**

把握した全体像から、必要な画面を列挙する。各画面について:

| 項目 | 内容 |
|------|------|
| 画面名 | 短い識別名（kebab-case） |
| タイトル | 人が読む名前 |
| Route | URL パスまたはハッシュルート |
| 目的 | この画面で何を達成するか（1文） |

列挙したらユーザーに「これで足りるか、追加したい画面はあるか」を確認する。

**Step 3: 各画面の操作定義**

画面ごとに操作を洗い出す。操作の粒度はユーザーが「それをやったら何が起きるか」を想像できるレベル。

| 操作 | 結果 | 遷移先 |
|------|------|--------|
| ○○をクリック | △△が表示される | （画面名 or なし） |
| ○○を入力 | △△が更新される | |

**Step 4: 画面遷移の整理**

全画面間の遷移を一覧化する。双方向遷移、条件付き遷移を明示する。

### 洗い出しのコツ

- **まず正常系を固める**: エラー画面や例外フローは後から追加
- **ユーザーの言葉で書く**: 技術用語より「○○ボタンを押す」「一覧が出る」
- **1画面1目的**: 1つの画面に複数の目的が混ざったら分割を検討
- **遷移の戻りを忘れない**: 「戻る」「キャンセル」「閉じる」も遷移

## Phase 2: ASCII ワイヤーフレーム生成

### 画面遷移図

全画面間の遷移を ASCII で描画する。

**フォーマット:**

```
┌─────────────┐
│  画面A      │
│  (/path-a)  │
└──┬──┬───────┘
   │  │
   │  └─── 操作名 ──→ ┌─────────────┐
   │                   │  画面B      │
   │                   │  (/path-b)  │
   │                   └─────────────┘
   │
   └─── 操作名 ──→ ┌─────────────┐
                    │  画面C      │
                    │  (/path-c)  │
                    └─────────────┘

※ 共通遷移は末尾に注記
```

### 各画面ワイヤーフレーム

画面ごとに ASCII ボックスアートでレイアウトを描画する。

**描画ルール:**

1. **外枠**: `┌─┐│└─┘` で画面全体を囲む
2. **ヘッダー**: 画面上部にタイトル・ナビゲーション
3. **セクション**: `┌─ セクション名 ─┐` でグループ化
4. **インタラクティブ要素**: `[ボタン名]`, `( ) ラジオ`, `[x] チェック`, `[入力欄____]`
5. **リスト項目**: `│ • 項目名 │` または `│ 1. 項目名 │`
6. **バッジ/ステータス**: `■` や `[tag]` で表現
7. **展開/折りたたみ**: `▼`（展開中）, `▶`（折りたたみ中）
8. **区切り線**: `├──────────┤` で横区切り

**サイズの目安:**
- 幅: 50〜60 文字（モノスペースで見やすい範囲）
- 1画面のワイヤーフレームは 20〜40 行

**良い例:**

```
┌──────────────────────────────────────────────────┐
│  ← 戻る                            project-name │
├──────────────────────────────────────────────────┤
│                                                  │
│  ユーザー一覧                                     │
│                                                  │
│  [検索____________________] [検索]                │
│                                                  │
│  ┌─ ユーザー (24件) ────────────────────────────┐ │
│  │ 田中太郎    admin   taro@example.com    [編集]│ │
│  │ 佐藤花子    user    hana@example.com    [編集]│ │
│  │ 鈴木一郎    user    ichi@example.com    [編集]│ │
│  │                    ...                       │ │
│  └──────────────────────────────────────────────┘ │
│                                                  │
│  ← 1 2 3 ... 8 →                                │
│                                                  │
│  [+ 新規ユーザー]                                 │
└──────────────────────────────────────────────────┘
```

### 操作一覧テーブル

全画面の操作を1つのテーブルにまとめる。

```markdown
| 画面 | 操作 | 遷移先/結果 |
|------|------|------------|
| Dashboard | screen カードクリック | Screen 詳細 |
| Dashboard | unit カードクリック | Unit 詳細 |
| Screen 詳細 | case 行クリック | 展開/折りたたみ |
| Screen 詳細 | given リンク | Setup 詳細 |
| 全画面 | ← 戻る | Dashboard |
| 全画面 | YAML 変更 | SSE で自動更新 |
```

## 出力フォーマット

最終成果物は以下の構成で Markdown ファイルとして出力する:

```markdown
# [機能名] — 画面設計

## 画面遷移フロー
（ASCII 遷移図）

## 各画面ワイヤーフレーム

### 1. [画面名] ([route])
（ASCII ワイヤーフレーム）

**操作:**
| 操作 | 結果 | 遷移先 |
|------|------|--------|

### 2. [画面名] ([route])
...

## 操作一覧（全画面）
（統合テーブル）
```

出力先はユーザーに確認する。デフォルト: `docs/wireframes/[feature-name].md`

---

## 注意点

- **ASCII アートの互換性**: 罫線文字（`┌─┐│└─┘├┤┬┴┼`）を使う。`+`, `-`, `|` の代替は見た目が崩れるので避ける
- **レスポンシブではない**: ASCII は固定幅。モバイル/デスクトップを分けたい場合は別ワイヤーフレームを作る
- **詳細度のバランス**: ピクセル単位の精度は不要。「何がどこにあるか」が伝わればよい
- **既存画面の参照**: コードベースに既存の画面があれば、Read で確認して整合性を取る
- **tespec YAML との連携**: ワイヤーフレーム完成後に `tespec-s03-yaml-gen` で YAML に落とせることを伝える
