# Dependency Analyst: パターン10案 依存関係評価

## 評価軸

- **依存方向の健全性**: 「不安定 → 安定」方向が保たれているか
- **循環依存リスク**: 誤った import を誘発しやすい構造になっていないか
- **変更局所性**: 新フレームワーク追加時の変更が最小モジュールに留まるか
- **モジュール境界の明確さ**: 責務が明確に分離されているか

スコア: ◎ 問題なし / ○ 条件付き問題なし / △ 注意が必要 / × 問題あり

---

## P01: 内部分岐（if/switch）

| 評価軸 | スコア | 理由 |
|---|---|---|
| 依存方向 | × | フレームワーク固有ロジックが1ファイルに混在し、モジュール境界が消える |
| 循環依存リスク | ◎ | ファイル数が増えないため循環依存は発生しない |
| 変更局所性 | × | 新フレームワーク追加のたびに `generator.ts` の複数箇所を変更 |
| モジュール境界 | × | normal/error/boundary の3タイプ × 関数数 × フレームワーク数で組み合わせ爆発 |

**総評**: 循環依存こそ起きないが、依存関係の問題を「ファイル内の複雑度」に転化するだけ。依存グラフは単純に見えて実態は絡み合っている。

---

## P02: 静的 Record Registry（合意案ベース）

| 評価軸 | スコア | 理由 |
|---|---|---|
| 依存方向 | ◎ | `commands/ → registry → generators/ → types/helpers → schema` の一方向 |
| 循環依存リスク | ◎ | `generator-types.ts` が独立しているため `generators/` が `registry` を import する必要がない |
| 変更局所性 | ◎ | 新フレームワーク追加は `registry.ts` の1行 + 新ファイルのみ |
| モジュール境界 | ◎ | 各 generator が独立ファイル。責務が1ファイル1フレームワークで明確 |

**総評**: 依存関係として最も健全。Step 1 合意通り。

---

## P03: Strategy パターン（クラスベース）

| 評価軸 | スコア | 理由 |
|---|---|---|
| 依存方向 | ○ | P02 と同等の方向性。abstract class が interface の代わりになるだけ |
| 循環依存リスク | ○ | abstract class を別ファイルに置けばリスクなし。同ファイルに混在させると増す |
| 変更局所性 | ○ | P02 と同等。registry への登録と新クラスの追加 |
| モジュール境界 | ○ | クラス継承により境界は明確だが、TypeScript では interface の方が軽量で十分 |

**総評**: P02 と依存関係上の差異は小さい。クラス継承を使う理由（共有ステートが必要など）がなければ P02 の関数ベースで十分。

---

## P04: Template Method パターン

| 評価軸 | スコア | 理由 |
|---|---|---|
| 依存方向 | ○ | `BaseGenerator → schema` の依存は安全 |
| 循環依存リスク | △ | `BaseGenerator` が `override` メソッドの戻り値型を定義するために サブクラスの型情報を知る必要が生じる場合がある |
| 変更局所性 | △ | `BaseGenerator` の骨格変更が全サブクラスに影響する。`BaseGenerator` 自体が変更の focal point になるリスク |
| モジュール境界 | △ | 共通フローが `BaseGenerator` に隠れるため、各フレームワークの実装を理解するのに継承チェーンを追う必要がある |

**総評**: `renderCase` 等の追加を `BaseGenerator` に集中させると、`BaseGenerator` 自体が「不安定な安定モジュール」になる矛盾が生じる。

---

## P05: 関数オブジェクト Registry（軽量変形）

| 評価軸 | スコア | 理由 |
|---|---|---|
| 依存方向 | ◎ | P02 と同等。型定義が薄くなるだけで方向は変わらない |
| 循環依存リスク | ◎ | interface がないため余計な import が発生しにくい |
| 変更局所性 | ○ | `fileExtension` 等のメタデータが別 Map になると管理が分散する |
| モジュール境界 | △ | `fileExtension` と `generate` 関数を別々に管理すると、追加フレームワーク時に両方の更新漏れリスクがある |

**総評**: P02 より型情報が少ない分、コンパイル時の整合性チェックが弱くなる。P02 の `FrameworkGenerator` interface は `generate + fileExtension + fileNameFor` を1箇所で管理できる点で優れる。

---

## P06: Builder パターン

| 評価軸 | スコア | 理由 |
|---|---|---|
| 依存方向 | △ | `TestFileBuilder` が内部で framework を保持し、`generate` 時にフレームワーク判定を行う場合、P01 の内部分岐と同じ問題に陥る可能性 |
| 循環依存リスク | ○ | Builder を独立クラスにすれば循環は起きない |
| 変更局所性 | △ | `setFramework()` の実装次第。Builder 内部に registry を持てば P02 相当になるが、その場合 Builder の存在価値が薄れる |
| モジュール境界 | △ | Builder の責務（フレームワーク選択 + 画面データ収集 + 出力）が広すぎる |

**総評**: テスト生成の文脈で Builder が有効になるのは「出力オプションが増えた時」。現時点では `generate(screen, setups)` の純粋関数性が高く、Builder の複雑さが不要。

---

## P07: Pipes & Filters

| 評価軸 | スコア | 理由 |
|---|---|---|
| 依存方向 | ○ | 各フィルター関数が独立すれば依存方向は健全 |
| 循環依存リスク | ○ | フィルターが互いに import し合わなければリスクなし |
| 変更局所性 | △ | フレームワーク差異が `renderFilter` 1つに収まるかどうかが設計の核心。差異が多いと複数フィルターに散在するリスク |
| モジュール境界 | △ | フィルターの「つなぎ方」を誰が知るか（パイプライン組み立て責務）が曖昧になりやすい |

**総評**: 関数型スタイルとして美しいが、テスト構造のレンダリングはステートフル（depth 管理等）なためパイプラインと相性が悪い部分がある。

---

## P08: Plugin / dynamic import（遅延ロード）

| 評価軸 | スコア | 理由 |
|---|---|---|
| 依存方向 | △ | `await import('./generators/${framework}.js')` は静的解析では依存関係が見えない。依存グラフツールが追跡できない |
| 循環依存リスク | △ | 静的解析不能のため、循環依存の検出が困難 |
| 変更局所性 | ◎ | registry への登録が不要で、ファイル追加だけで拡張できる |
| モジュール境界 | △ | モジュール境界が動的になり、型安全性が低下する。`platform-expert` の評価と重なるが依存関係の可視性が最も低い |

**総評**: 依存関係の静的追跡が失われる点が依存関係アナリストとして最大の懸念。`madge` 等のツールも機能しなくなる。

---

## P09: テンプレートエンジン（Handlebars / EJS）

| 評価軸 | スコア | 理由 |
|---|---|---|
| 依存方向 | △ | テンプレートファイル（`.hbs`/`.ejs`）はモジュールシステムの外に置かれる。依存関係が TypeScript の import グラフに現れない |
| 循環依存リスク | ◎ | テンプレートファイルは import しないため循環依存は起きない |
| 変更局所性 | ◎ | テンプレートファイルの追加だけで新フレームワーク対応 |
| モジュール境界 | △ | ロジック（TS）とテンプレート（テキスト）の境界が実行時にしか確認できない。型安全性ゼロ |

**総評**: 依存関係が TypeScript のモジュールシステムから外れるため、コンパイル時の整合性チェックが失われる。テスト構造の複雑さ（depth管理・use:参照解決）をテンプレートで表現しきれない可能性も高い。

---

## P10: AST / CodeWriter ベース

| 評価軸 | スコア | 理由 |
|---|---|---|
| 依存方向 | ◎ | AST ノード定義 → Printer の方向は依存関係として理想的 |
| 循環依存リスク | ◎ | AST ノードは純粋なデータ構造なので循環依存が起きにくい |
| 変更局所性 | ◎ | 新 Printer の追加だけで新フレームワーク対応 |
| モジュール境界 | ◎ | AST（意味表現）と Printer（出力形式）が明確に分離される |

**総評**: 依存関係として最も理想的な構造だが、実装コストが他のすべての案を大幅に上回る。現在の `generator.ts` 規模では過剰。

## 推奨順位

1. **P02** — 依存関係の全軸で最高評価。実装コストも低い。合意案として妥当
2. **P05** — P02 の軽量版。型情報が薄い分 P02 に劣るが依存方向は同等
3. **P03** — クラスベースが必要なら。P02 と依存方向の差異は小さい
4. **P10** — 将来スケールするなら理想的。現時点では過剰
5. **P01** — 採用不可（依存関係の問題をファイル内複雑度に転化するだけ）
