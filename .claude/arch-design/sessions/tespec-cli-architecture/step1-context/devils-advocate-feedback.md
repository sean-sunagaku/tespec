# Devils Advocate: YAGNI 警告・批判レビュー

**担当**: devils-advocate
**対象**: tespec-design.md + future-plans.md
**観点**: YAGNI / KISS 原則 — 本当にそこまで複雑にする必要があるか？

---

## 総評

現在の設計は「仕様書 as YAML」という核心的価値に対して、**ステータス管理・遷移図・CLI 5コマンドという3つの独立した責務**が混在している。v1 として公開するなら、これは過剰設計の典型パターン。

---

## 批判 1: future-plans.md の機能は v1 に不要

### priority フィールド

**問題**: 「どこから書くか」の判断材料になる、という説明だが、これは開発者が自分で決められる。priority フィールドを YAML スキーマに追加すると、バリデーションの対象が増え、「バリデーションの信頼性」というコアバリューの実装コストが増大する。

**代替案**: v1 では priority を省く。「テストケースの並び順が priority」という慣習で十分。

### AI プロンプト生成（`tespec next --format prompt`）

**問題**: これは CLI ツールの責務ではなく、AI エージェントのプロンプトエンジニアリングの問題。v1 で実装すると、プロンプトフォーマットの変更のたびにツール側を修正することになる。

**代替案**: v1 では `tespec generate` で生成したスケルトンを AI に渡す。プロンプト生成はユーザーに委ねる。

### GitHub Actions 連携

**問題**: OSS として広く使ってもらう前に、特定の CI プラットフォームに依存する機能を v1 に含めると、「まず動くものを公開して使われ方を見る」という機会が失われる。actions のメンテナンスコストも発生する。

**代替案**: `tespec status --format json` の出力だけ v1 で用意し、Actions 連携はユーザーが自分で組む。公式 Action は v2 以降。

---

## 批判 2: CLI 5コマンドは多すぎる

### 現在の設計

`status` / `validate` / `sync` / `generate` / `diagram` の 5 コマンド。

### 問題

v1 で 5 コマンドを同時リリースすると、各コマンドの仕様決定・実装・テスト・ドキュメントコストが 5 倍になる。利用者にとっても「最初に何を使えばいいか」が不明確になる。

### 本当に v1 に必要なコマンドの考察

| コマンド | v1 必要性 | 判断理由 |
|---|---|---|
| `validate` | **必須** | コアバリュー「バリデーションの信頼性」そのもの |
| `generate` | **必須** | YAML から何か出力するという核心的ユースケース |
| `status` | **要検討** | `.status.json` が存在して初めて意味を持つ |
| `sync` | **要検討** | テストランナーとの統合が必要。v1 の範囲外の可能性 |
| `diagram` | **後回し可** | ドキュメント化機能。核心価値とは独立 |

**代替案**: v1 は `validate` + `generate` の 2 コマンドのみ。`status` / `sync` / `diagram` は v2。

---

## 批判 3: YAML スキーマの `not_expect` と `navigates_to` は v1 に必要か？

### `not_expect`

**問題**: 「起きてはいけないこと」を YAML に書くこと自体は有意義だが、v1 の `generate` コマンドはスケルトンを生成するだけ。`not_expect` を生成されたテストコードにどう反映するかが未定義のまま、スキーマだけ先に生やすのは YAGNI の典型的な違反。

**代替案**: v1 では `not_expect` をスキーマから除く。コメントとして `action` / `expect` に含める慣習で代替。v2 で正式フィールド化。

### `navigates_to`

**問題**: `navigates_to` は遷移図生成（`diagram` コマンド）のためにのみ存在するフィールド。もし `diagram` コマンドを v2 に後回しにするなら、`navigates_to` も v1 スキーマに入れる必要はない。

**代替案**: `diagram` コマンドを v2 に移すなら `navigates_to` も v2 スキーマに追加。もし `diagram` を v1 に含めるなら `navigates_to` は必要。セットで扱うべき。

### `type` フィールド

**問題**: `normal` / `error` / `boundary` の分類は設計として理解できる。ただし `type` のバリデーション（`type: error` が 0 件なら warning）を実装すると、「型を正しく使っているかのチェック」という複雑なバリデーションロジックが必要になる。

**代替案**: v1 では `type` は記録するだけにとどめ、0 件 warning のようなセマンティックバリデーションは v2 以降。

---

## 批判 4: ステータス管理（`.status.json`）は v1 に必要か？

### 問題

`.status.json` を機能させるには `sync` コマンドが必要で、`sync` はテストランナー（Playwright 等）との連携が必要。つまり「テストランナーの実行結果を解析して .status.json に書き込む」という非自明な統合問題が v1 に混入する。

v1 ユーザーの最初のユースケースは「YAML を書いてテストスケルトンを生成し、Playwright でテストを書く」であるはずで、`sync` や `status` はその後の話。

### 代替案

v1 では `.status.json` を完全に除外する。スキーマもステータス管理もなし。`validate` と `generate` だけで「YAML が正しいかチェックし、テストスケルトンを生成する」という価値を届ける。`.status.json` は v2 以降でテストランナー連携と一緒に設計する。

---

## 批判 5: モジュール分割のリスク

### 懸念

設計書のファイル構成（`screens/`, `setups/`, `config.yaml`）は適切だが、実装レベルでモジュールを過剰分割するリスクがある。特に CLI ツールのような「スクリプト的なユースケース」では、抽象化のレイヤーが増えるほど「読んで理解するコスト」が増大する。

OSS として公開する場合、コントリビューターがコードを読んで理解できることが重要。

### 代替案

実装は以下の 3 層のみに抑える：
1. **CLI エントリポイント** (`cli.ts`) — コマンドのルーティング
2. **Core ロジック** (`core/`) — YAML パース・バリデーション・生成
3. **ユーティリティ** (`utils/`) — ファイル IO 等

「サービス層」「リポジトリ層」のような Web バックエンド的な抽象化は不要。

## まとめ: v1 の最小構成案

| 項目 | v1 に含める | v2 以降 |
|---|---|---|
| YAML スキーマ（`action` + `expect` + `given` + `target` + `type`） | yes | — |
| `not_expect` フィールド | no | v2 |
| `navigates_to` フィールド | `diagram` を含む場合のみ | — |
| `validate` コマンド | yes | — |
| `generate` コマンド | yes | — |
| `status` コマンド | no | v2 |
| `sync` コマンド | no | v2 |
| `diagram` コマンド | **要議論** | v2 候補 |
| `.status.json` 管理 | no | v2 |
| `priority` フィールド | no | v2 |
| AI プロンプト生成 | no | v2 |
| GitHub Actions 連携 | no | v2 |

**最小 v1 の価値提案**: 「YAML で画面仕様を定義し、整合性をバリデーションし、テストスケルトンを生成する」。これだけで十分に価値がある。

## architecture-lead へのお願い

Step 2（パターン比較）に進む前に、以下の 2 点を決定してほしい：

1. **`diagram` コマンドは v1 か v2 か？** — これが決まると `navigates_to` フィールドの要否が確定する
2. **`.status.json` と `sync` は v1 スコープに含めるか？** — これが決まると「ステータス管理」の設計工数が明確になる

v1 のスコープを絞れば、Step 3（モジュール設計）の複雑さも大きく下がる。
