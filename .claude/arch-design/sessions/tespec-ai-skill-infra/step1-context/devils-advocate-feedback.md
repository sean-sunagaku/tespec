# Devils Advocate フィードバック: YAGNI/過剰設計チェック

## コードベース現状把握

- src/ 以下: 8 ファイル（cli.ts + commands/2 + core/4 + utils/1）
- 既存コマンド: `tespec validate`、`tespec generate` の 2 つのみ
- フレームワーク: oclif（サブコマンド構造は既に確立済み）
- スキーマ: Zod で Screen/Case/Setup/Config を定義
- バリデーション: `validator.ts` に 7 種のチェック関数

---

## 要件 1: AI Skill（SKILL.md + references）の作成

### 本当に必要か？
**YES（最小限なら）**。ただし、問題は「references」が複数ファイルを示唆している点。

### 過剰設計リスク
- SKILL.md 1 ファイルで十分なはず
- references を別ファイルに分割する理由が今の段階では不明
- schema.ts は 38 行しかない。リファレンスドキュメントを作るほどの複雑さではない

### 最もシンプルな代替案
SKILL.md 1 ファイルのみ。以下を含める：
- YAML の書き方サンプル
- schema.ts から直接抽出したフィールド定義
- バリデーションルール一覧
references フォルダは「将来スキーマが複雑化したとき」に作ればいい

---

## 要件 2: npx で Skill を配布するコマンド

### 本当に必要か？
**疑問あり**。優先度が最も低い要件。

### 過剰設計リスク
- 現状の「配布」需要が不明。ユーザーは何人いるか？
- npx インストーラーは実装コスト高（新しい npm パッケージ or 新コマンド）
- oclif にサブコマンドを追加するなら、テスト・ドキュメント・型定義すべてを追加する必要がある

### 最もシンプルな代替案
**シェルスクリプト 1 本** または **README に手順を書く**だけで十分：
```sh
# README に書く
curl -o SKILL.md https://raw.githubusercontent.com/sean-sunagaku/tespec/main/SKILL.md
```
npx 配布コマンドは「配布需要が実際に発生してから」考える。今は YAGNI。

---

## 要件 3: バリデーションスクリプト

### 本当に必要か？
**ほぼ重複している**。

### 過剰設計リスク
`tespec validate` が既に存在する。validator.ts には 7 種のバリデーション関数がある。
「バリデーションスクリプト」が `tespec validate` と何が違うのかが不明。

### 最もシンプルな代替案
- もし「SKILL.md 自体のバリデーション」なら、そもそも Markdown ファイルは構造が単純なので手動確認で十分
- もし「YAML スキーマのバリデーション強化」なら、既存 `validator.ts` に関数を追加するだけ
- 新しいスクリプトを作る前に、`tespec validate` で何が不足しているかを明確にすべき

---

## 要件 4: スキーマ変更時の自動更新

### 本当に必要か？
**NO（今は）**。最も過剰な要件。

### 過剰設計リスク
- スキーマ（schema.ts）の変更頻度は不明。まだ v0.1.0
- 「自動更新」の実装には CI/CD パイプラインか watch スクリプトが必要
- そもそも「何を自動更新するのか？」が曖昧: SKILL.md？テスト？リファレンス？
- スキーマが安定していない段階で自動化しても、自動化コードのメンテナンスコストが発生するだけ

### 最もシンプルな代替案
**`pnpm run update-skill` という npm script 1 本**：
```json
"update-skill": "node scripts/generate-skill.js"
```
実行は手動。「自動更新が欲しい」と感じる頻度が高くなってから CI 連携を考える。

---

## 4 つの要件を同時に出す必要があるか？

### 答え: NO

段階的に出すべき順序：

**Phase 1（今すぐ）**
- SKILL.md を手書きで作る（1 ファイル、references なし）
- それだけで AI が tespec YAML を生成できるか検証する

**Phase 2（検証後）**
- バリデーション強化（`tespec validate` で不足している部分が判明してから）
- 手動更新スクリプト（SKILL.md が実際に陳腐化する頻度を見てから）

**Phase 3（需要確認後）**
- npx 配布コマンド（複数ユーザーへの配布需要が発生してから）
- 自動更新 CI（手動スクリプトが面倒に感じるくらいの頻度になってから）

---

## まとめ: 最もシンプルな全体代替案

```
SKILL.md（1 ファイル、手書き）
   ↓ 検証して陳腐化したら
scripts/generate-skill.js（手動実行スクリプト）
   ↓ 頻度が高くなったら
CI での自動更新
   ↓ 配布需要が発生したら
npx 配布コマンド
```

**今すぐ必要なのは SKILL.md 1 ファイルだけ。** 残りは全て「そうなってから考える」案件。

---

## 設計チームへの勧告

1. **要件の同時実装を禁止する**。Phase 1 の SKILL.md 検証が完了するまで他の要件の設計を始めない
2. **references フォルダの設計を今するな**。schema.ts が 38 行しかない今、1 ファイルで管理できる
3. **配布コマンドに oclif サブコマンドを追加するな**。README の curl コマンドで十分
4. **「自動」という言葉が出たら立ち止まれ**。手動で十分かを必ず検証すること
